# Kirameku 单体化重写方案

> 文档状态：设计稿（已实施；旧后端已下线）
> 编写日期：2026-10-20
> 适用仓库：`Kirameku-HomePage`
> 目标：把当前「Next.js 前台 + FastAPI 后端 + Vue 管理后台 + Kotlin 阅读服务」重写为**单语言、单进程、单数据库**的单体应用；**小说模块下线，不迁移**。
> 数据库决策：**SQLite 3（WAL 模式，单文件）**，替换 PostgreSQL；数据一次性迁移，保留 PG 冷备份用于回滚。
>
> **2026-10-22 状态：** 本方案中的 `Kirameku-backend/`、PostgreSQL 一次性迁移脚本和 `migrate:audit` / `migrate:pg2sqlite` 命令已下线；涉及这些内容的章节仅作历史设计记录。当前运行、部署和数据库维护以 [`README.md`](../README.md)、[`AGENTS.md`](../AGENTS.md)、[`DEPLOY_NOTES.md`](../DEPLOY_NOTES.md) 和 [`Kirameku/server/db/README.md`](../Kirameku/server/db/README.md) 为准。

## 0. 结论摘要

### 0.1 推荐方案

**用 TypeScript 重写为 Next.js 16 单体应用。**

| 项目 | 现状 | 目标 |
|:-----|:-----|:-----|
| 应用语言 | TypeScript / Python / Vue / Kotlin | **TypeScript** |
| 可部署单元 | Next 前台、FastAPI、Vue 静态后台、reader-master | **1 个 Node 进程** |
| 进程/端口 | 3000 + 8000 + 8085（+ Nginx） | **3000（+ Caddy）** |
| 数据库 | PostgreSQL 16 | **SQLite 3（WAL，单文件）** |
| 管理后台 | Vue 3 + Element Plus + Pure Admin | **React 19 + Tailwind 4 + shadcn/ui** |
| 前台 | Next.js 16 App Router | **保留并重构数据层** |
| 后端 API | FastAPI + SQLModel | **Next Route Handlers + Server Actions + Drizzle** |
| 阅读服务 | Kotlin/Spring Boot（外部） | **下线（不迁移）** |
| 部署 | 多进程 + 多段 Nginx 反代 | **单进程容器 + CI 构建镜像 + 单段 Caddy 反代** |

### 0.2 关键判断

1. **语言必须是 TypeScript。** 前台约 3.1 万行 React/Next 代码是项目最大的资产，改用 Python/Go/Java 都意味着连 UI 和动画一起重写，成本约是保留 React 的 2–3 倍。TypeScript 可以同时覆盖前台、API、后台、脚本、测试，是唯一能实现「同一种语言 + 复用现有 UI」的选项。
2. **单体不等于把所有代码塞进一个目录。** 推荐「一个可部署单元 + 清晰模块边界」：Next 负责路由/渲染，`server/modules/*` 承载领域逻辑，`server/db` 承载数据访问。后续如果某个模块要拆出去，边界已经存在。
3. **数据库换成 SQLite，但不是「无痛切换」。** 目标库是**单文件 SQLite（WAL 模式）**，不再保留 PostgreSQL 运行时。表名、字段名、可空性和业务语义保持不变，类型按 SQLite 亲和类型映射；现有数据用一次性导出/导入脚本迁移，并做行数、ID、内容哈希校验。换库的收益是零外部 DB 进程、备份即文件、本地开发零依赖，代价是**单写者、只能单实例、不能放 NFS**——这与本项目「单进程」的目标一致。迁移必须安排维护窗口，并保留 PostgreSQL 冷备份用于回滚（见 §5.5、§12.3、§12.4）。
4. **小说模块已决定下线，不迁移。** 现有 `reader-master` 是外部 Kotlin 服务，不在本仓库；经过评估，本次不保留小说功能，也不实现 legado 规则引擎。这样可以直接消除一个隐性单点、GPL/抓取合规风险和约 8–10 人日的工程量。相关页面、API、Nginx 路由和进程一并移除，旧 `/novel/*` 与 `/reader3/*` 直接删除并返回 404（见 §8.5）。因此最大的风险转移到**数据迁移**和**后台重写**。
5. **顺手修掉当前的安全问题。** 现有实现存在「GitHub 用户 token 可访问管理接口」「访客删除接口完全无鉴权」「管理员默认密码 admin123」「token 放在 URL/localStorage/JS 可读 Cookie」等 P0 问题，重写时必须一并修复（见 §7.9）。

### 0.3 工作量预估

| 范围 | 预估 |
|:-----|:-----|
| 单体化重写（不含小说；小说下线） | **约 31–37 人日** |
| 小说模块迁移 | **不迁移**；仅做下线清理（0.5–1 人日，已计入） |
| 单人节奏 | 约 7–8 周 |
| 两人并行（前台/后台分线） | 约 5 周 |

> 相比保留 PostgreSQL 的版本，增加了约 2 人日：一次性导出/导入脚本、类型/时区转换、校验清单、切流与回滚演练。SQLite 同时也省掉了连接池、DB 进程和 Testcontainers 相关的运维与 CI 成本。
>
> 相比原计划，去掉了小说规则引擎 spike、P4（8d）和小说相关测试/运维；小说只保留「下线」工作量（移除导航、路由、rewrite、reader-master 进程、旧 URL 处理）。

### 1.5 现有痛点

**架构与部署**

1. 三种应用语言（TypeScript、Python、Kotlin）+ 一套 Vue 后台，四套依赖、四套构建、四个进程。
2. `next.config.ts` 里用 rewrites 把 `/api`、`/uploads`、`/reader3` 分别代理到 8000/8085；生产环境又由 Nginx 重复代理。任何一段配置不一致都会出现 `DEPLOY_NOTES.md` 记录的 Mixed Content、旧 HTML 缓存问题。
3. 前台同时存在三套 API 地址来源：
   - `siteConfig.apiBaseUrl`（`Kirameku/app/api/client.ts:3`）
   - `NEXT_PUBLIC_API_URL`（`Kirameku/app/page.tsx:3`）
   - 硬编码 `http://127.0.0.1:8000`（`Kirameku/app/feed/route.ts:8`）
4. `reader-master` 不在仓库内，无法做版本锁定和本地一键启动，是隐性单点；**本次直接下线该模块**，不再维护。
5. 数据库没有迁移工具：`SQLModel.metadata.create_all` + 手工 `init_db.sql`，两者已经存在漂移风险；同时 PostgreSQL 需要独立进程/实例，本地开发、备份、监控都要多一层依赖。

**性能与数据访问**

6. 除首页三个计数外，几乎所有页面都是 `"use client"` + `useEffect` 拉数据，首屏依赖 JS 和水合，SEO/弱网体验一般。
7. 后端存在 N+1：文章列表逐篇查分类/标签、评论逐条查 GitHub 用户、后台评论逐条递归查回复。
8. 没有缓存层；RSS 每次请求都逐篇拉文章详情；首页每次重新拉计数。
9. 文章浏览量在 GET 详情时自增，新方案如果直接 SSR，`<Link prefetch>` 会误增浏览量，需要单独设计（见 §8.1）。
10. `category.post_count`、`tag.post_count`、`chatter.comments_count` 等冗余计数没有事务性保证，会漂移。

**安全（重点）**

11. **管理接口鉴权可绕过**：`app/utils/auth.py:32` 的 `get_current_user` 只验签，不校验 `type/aud` 和 `is_admin`；而 GitHub 用户 token 用同一个 `SECRET_KEY` 签发（`app/api/github_auth.py:95`）。因此任何 GitHub 登录用户拿到的 token 都可能调用 `/api/posts` 的写接口和后台管理接口。
12. **访客删除无鉴权**：`app/api/visitors.py:61`、`:71` 的 DELETE 接口没有 `Depends(get_current_user)`，任何人都能删除/清空访客记录。
13. **默认管理员密码**：`init_db.sql:302` 写入 `admin / admin123`。
14. **token 暴露面过大**：GitHub 登录把 token 放在 URL query（`github_auth.py:102`），前端存入 `localStorage`；管理后台把 accessToken 放在 JS 可读的 Cookie（`authorized-token`）并配合 localStorage 元信息，一旦 XSS 即可被读走。
15. **CORS 跨源 + 凭据**：`app/main.py:20` 允许携带凭据的跨源请求；改成同源单体后应彻底删除 CORS。
16. **上传校验不足**：`app/api/upload.py:20` 允许 SVG，且只信任 `Content-Type`，存在存储型 XSS/伪装文件风险。
17. **公开写接口无限流**：登录、评论、留言、点赞、访客记录都没有速率限制。
18. **Markdown 直接 `dangerouslySetInnerHTML`**：`Kirameku/app/posts/[slug]/page.tsx:367`、`app/about/page.tsx:158` 未做 HTML 清洗。文章由管理员撰写，风险相对低，但仍是纵深防御缺口。
19. **访客 IP 长期明文存储**，没有保留期限/脱敏策略。
20. **`/api/uapis` 是外部 API 代理**，路径参数未做白名单，存在被滥用为开放代理的风险。

**功能一致性**

21. ~~前台 `/projects` 用静态 `projectsData.ts`，后台却维护 `project` 表，后台改动不会生效。~~ 已解决：`/projects` 改为读 `project` 表，原静态数据通过 `0001_seed_projects.sql` 一次性种子导入。
22. 后台站点配置页维护 `site_config`，前台却只读 `siteConfig.ts`，两套配置源。
23. 管理后台 API 返回 `{code,message,data}`，公开 API 返回裸对象/数组，错误格式也不统一。
24. 后台模板包含大量未使用的系统管理/权限/监控页面，增加构建体积和维护噪音。
25. 没有自动化测试、没有 CI、没有迁移回滚脚本。

## 2. 目标与约束

### 2.1 目标

| 编号 | 目标 | 验收方式 |
|:-----|:-----|:---------|
| G1 | **单语言**：应用代码（含脚本、测试）全部为 TypeScript | 仓库内无 `.py`、`.vue`、`.kt` 运行时代码；SQL/Nginx/Docker 配置除外 |
| G2 | **单进程**：一个 Node 进程提供页面 + API + 后台 | 生产只有 `node server.js`（Next standalone） |
| G3 | **功能对等**：前台、后台、RSS、上传、访客全部可用（小说模块除外） | 功能清单逐项验收 |
| G4 | **数据零丢失**：PostgreSQL 全量数据成功迁移到 SQLite，OSS 资源不变 | 行数/ID/内容哈希/外键校验一致 |
| G5 | **安全修复**：P0 问题全部关闭 | 安全测试用例通过 |
| G6 | **可回滚**：切流失败可在 30 分钟内回旧系统 | 回滚演练通过（含 SQLite→旧栈） |
| G7 | **可维护**：模块边界清晰、有迁移、有测试、有 CI | 新成员可按文档本地启动 |
| G8 | **单文件数据**：SQLite 文件可在线备份/恢复 | 备份恢复演练通过 |

### 2.2 非目标

- 不重做视觉设计。前台现有的 Glassmorphism、动画、Live2D、工具箱全部保留。
- 不引入微服务、消息队列、Redis、Kubernetes。
- 不做多用户/多租户；仍是单博主 + GitHub 访客评论。
- 不新增大型业务功能（如全文搜索、AI 摘要）；只做架构重写与必要修复。
- **不保留小说模块**：不迁移 `reader-master`，不实现 legado 规则引擎；`/novel/*` 与 `/reader3/*` 下线。
- 不改变现有内容页 URL（`/posts/[slug]` 等），避免 SEO 损失；小说旧 URL 直接删除并返回 404。

### 2.3 约束

| 约束 | 影响 |
|:-----|:-----|
| 生产服务器 1.8GB 内存 | 构建必须在本地/CI 完成；运行时限并发；不做多实例 |
| 现有域名 `boke.hiromu.top` | 保持 URL；OSS 旧图片域名继续可用 |
| 已有 PostgreSQL 数据 | 需一次性导出并导入 SQLite；字段名/可空性保持，类型映射 |
| SQLite 单写者 | 同一时刻只有一个写事务；写操作必须短小；不能多实例/多副本 |
| SQLite 数据文件 | 必须放本地 SSD/持久卷，禁止 NFS/对象存储挂载；单文件备份 |
| GitHub OAuth 已配置 | 回调地址需在 GitHub 后台更新为单一域名 |
| 单博主运营 | 后台不需要 RBAC/多角色；只需要 admin/visitor 两种身份 |
| 小说模块下线 | 不迁移 `reader-master`；旧 `/novel/*`、`/reader3/*` 返回 404；不再有 8085 端口 |

## 3. 技术选型

### 3.1 方案对比

| 方案 | 前台复用 | 单语言 | 单进程 | 工作量 | 风险 | 结论 |
|:-----|:--------:|:------:|:------:|-------:|:-----|:-----|
| **TypeScript + Next.js 16 单体** | ★★★★★ | ★★★★★ | ★★★★★ | 中 | 低 | **推荐** |
| TypeScript + NestJS API + React SSR | ★★★★ | ★★★★★ | ★★★（可同进程，但需自建 SSR） | 中高 | 中 | 不必要，Next 已覆盖 |
| Python + FastAPI + Jinja/HTMX | ★（需重写全部 UI） | ★★★★★ | ★★★★★ | 很高 | 高 | 会丢掉动画/组件资产 |
| Go + templ + HTMX | ★ | ★★★★★ | ★★★★★ | 很高 | 高 | 同上，且生态不匹配 |
| Java/Spring + Thymeleaf | ★ | ★★★★★ | ★★★★★ | 很高 | 高 | 同上，运维更重 |

**结论：TypeScript + Next.js 16。** 这不是「为了单体而单体」，而是现有资产约束下的最优解：

- 前台 3 万行 React 组件、动画、工具箱可以继续用。
- Next 的 Route Handlers / Server Actions 可以直接替代 FastAPI。
- App Router 的 Server Components 让「页面直接查库」成为可能，减少一层 HTTP。
- 一个 `next build` + 一个 `node server.js` 就是完整应用。

### 3.2 目标技术栈

| 层 | 选型 | 说明 |
|:---|:-----|:-----|
| 运行时 | Node.js 22 LTS（或 24 LTS） | 与 Next 16 / 现有依赖兼容 |
| 包管理 | pnpm 9+ | 现有前台/后台都用 pnpm |
| 框架 | Next.js 16 App Router | 页面、Route Handlers、Server Actions |
| UI | React 19 + Tailwind CSS 4 | 前台沿用；后台新增 shadcn/ui |
| 语言 | TypeScript 5.9+，`strict: true` | 全仓库统一 |
| 数据库 | **SQLite 3.45+（WAL 模式，单文件）** | 无独立 DB 进程；单写者；见 §5.1 |
| ORM | **Drizzle ORM + better-sqlite3** | 同步 API、开销低；通过 `serverExternalPackages` 保持原生模块 |
| 迁移 | drizzle-kit（SQLite dialect） | 版本化 SQL 迁移；空库一键初始化 |
| 校验 | zod | API 入参、表单、环境变量 |
| 认证 | jose（JWT）+ bcryptjs | httpOnly Cookie；兼容现有 bcrypt 哈希 |
| 管理 UI | shadcn/ui + Radix + TanStack Table + react-hook-form | 不引入第二套 Vue |
| 编辑器 | CodeMirror 6（已有依赖）+ marked + highlight.js | Markdown 编辑/预览 |
| 图表 | recharts（已有依赖） | 仪表盘 |
| 图片 | ali-oss + sharp | OSS 上传、方向识别、压缩 |
| 缓存 | Next Cache Components（`use cache`/`cacheTag`）或 `unstable_cache` | 页面/查询缓存 |
| 日志 | pino | JSON 结构化日志 |
| 测试 | Vitest + Playwright + 临时 SQLite 文件 | 单元/集成/E2E；无需 Testcontainers |
| 代码质量 | ESLint + Prettier + `tsc --noEmit` | CI 门禁 |

**数据库选型说明：**

- 单博主、单实例、数据量小（文章/评论/访客），SQLite 的并发能力足够；WAL 模式下读不阻塞写。
- 去掉独立 PostgreSQL 进程后，1.8GB 服务器更宽裕，部署只剩「Node 容器 + 数据卷 + Caddy」。
- 备份从 `pg_dump` 变成**在线备份 API + 单文件上传**，恢复更快。
- 代价必须接受：**只有一个写者**、**只能跑一个实例**、**不能把数据文件放 NFS**、**长事务会阻塞写入**。这些约束与「单进程单体」一致，但要在代码和部署上明确禁止多副本。

> 驱动选择：一期用 `better-sqlite3`（同步、成熟、Drizzle 支持好）。它是同步 API，会阻塞事件循环，因此要求单查询 P95 < 20ms、批量写入合并事务、禁止在请求路径做全表扫描。若后续出现明显 event loop lag，再评估 `node:sqlite` 或 worker thread，不在一期引入。

### 3.3 为什么是 Drizzle，不是 Prisma

| 维度 | Drizzle | Prisma |
|:-----|:--------|:-------|
| 运行时 | 轻量，直接生成 SQL | 需要 query engine，内存占用更高 |
| 现有 schema | 贴近现有 SQL，迁移可控 | 需要 schema 重写 |
| 复杂聚合 | 直接写 SQL 模板 | 部分场景受限 |
| 1.8GB 服务器 | 更友好 | 偏重 |

Drizzle 的 schema 与现有表一一对应，SQLite 方言的迁移文件可读、可审查；配合 `better-sqlite3` 也没有额外运行时引擎，适合 1.8GB 服务器。

### 3.4 为什么不需要 tRPC / GraphQL

- 前后端在同一个应用里，Server Components 可以直接调用 service，不需要 RPC 层。
- 公开 API 仍需 REST（RSS、潜在第三方、客户端分页/点赞）。
- 引入 tRPC 会增加一层类型胶水，收益有限；如果未来需要，可在 `server/modules` 之上再加。

## 5. 数据层设计

### 5.1 原则

1. **表名、字段名、可空性、业务语义不变。** 旧系统仍是回滚目标；类型按 SQLite 亲和类型映射（见下表）。
2. **空库重建，不做 PostgreSQL baseline。** 新库由 Drizzle 迁移从零创建，再把 PostgreSQL 数据一次性导入；不修改旧库。
3. **迁移文件化。** 所有 schema 变更必须通过 `drizzle-kit generate` 生成 SQL，禁止手工改生产库。
4. **写事务短小。** SQLite 只有一个写者；文章+标签、相册+照片计数、评论+计数等必须在同一事务内完成，但事务里不做网络请求、不 `await`。
5. **数据库是唯一事实来源。** 删除 `projectsData.ts`、`siteConfig` 中与 DB 重复的数据；静态品牌配置除外。
6. **时间统一。** 所有时间字段存 **UTC epoch milliseconds（INTEGER）**，由应用侧 `Date.now()` 生成；不再依赖数据库 `NOW()` 或服务器时区。
7. **连接单例。** 每个 Node 进程只创建一个 `better-sqlite3` 连接；开发环境用 `globalThis` 缓存，避免 HMR 重复打开文件。

#### 5.1.1 PostgreSQL → SQLite 类型映射

| PostgreSQL | SQLite | 说明 |
|:-----------|:-------|:-----|
| `SERIAL` | `INTEGER PRIMARY KEY AUTOINCREMENT` | 保留原 `id`；导入时显式写入 id |
| `VARCHAR(n)` | `TEXT` | SQLite 不强制长度；由 zod 校验，必要时加 `CHECK(length(col) <= n)` |
| `TEXT` | `TEXT` | 正文、JSON 字符串、URL 等 |
| `INTEGER` | `INTEGER` | 64 位有符号 |
| `BOOLEAN` | `INTEGER`（0/1） | Drizzle `integer({ mode: "boolean" })`；加 `CHECK (col IN (0,1))` |
| `TIMESTAMP` | `INTEGER`（epoch ms, UTC） | 导出时用 `EXTRACT(EPOCH FROM (col AT TIME ZONE 'Asia/Shanghai')) * 1000`；`timestamp without time zone` 的 `EXTRACT(EPOCH)` **不受会话时区影响** |
| `TIMESTAMPTZ` | `INTEGER`（epoch ms, UTC） | 现有库未使用；新表统一 UTC ms |
| `JSONB` | `TEXT` | 存 `JSON.stringify` 结果；加 `CHECK (json_valid(col))` |
| `NUMERIC` / `BYTEA` | `REAL` / `BLOB` | 现有 18 张表未使用 |

> **可空性以生产库为准。** `init_db.sql` 里很多列只有 `DEFAULT` 没有 `NOT NULL`，实际数据可能存在 `NULL`。写 Drizzle schema 前先跑 `information_schema.columns` 审计，不要在 SQLite 里擅自加 `.notNull()`，否则导入会失败。

#### 5.1.2 SQLite 运行参数

每个连接建立后立即设置（`journal_mode` 会写进数据库文件，其余是连接级）：

```sql
PRAGMA journal_mode = WAL;          -- 读写并发；崩溃恢复更好
PRAGMA synchronous = NORMAL;        -- WAL 下的推荐值；断电可能丢最后若干事务，但不损坏
PRAGMA foreign_keys = ON;           -- SQLite 默认关闭，必须每个连接打开
PRAGMA busy_timeout = 5000;         -- 写锁等待 5s，超时返回 SQLITE_BUSY
PRAGMA cache_size = -20000;         -- 约 20MB page cache
PRAGMA mmap_size = 268435456;       -- 256MB 内存映射
PRAGMA temp_store = MEMORY;         -- 小排序/临时表放内存
```

建库时额外设置：

```sql
PRAGMA auto_vacuum = INCREMENTAL;   -- 必须在建表前设置；之后用 incremental_vacuum 回收
```

运行期约束：

- 写事务显式使用 immediate 模式（Drizzle：`db.transaction(fn, { behavior: "immediate" })`；原生 better-sqlite3：`db.transaction(fn).immediate()`），避免读锁升级写锁时死等。
- 单条写事务控制在 **50ms** 内；批量导入/相册照片写入用一次事务，不要逐条提交。
- 长查询（导出、统计、备份）放到维护脚本或低峰期；WAL 下读不阻塞写，但长读会阻止 WAL checkpoint。
- `SQLITE_BUSY` 不直接抛 500：写接口做 2–3 次短退避重试，仍失败返回 `503 DB_BUSY`；读接口直接重试一次。
- 每日低峰执行 `PRAGMA optimize;`；每周执行 `PRAGMA incremental_vacuum(1000);` 并检查 `-wal` 大小。
- 数据文件必须在本地 SSD；**禁止 NFS/SMB/对象存储挂载**，否则锁语义不可靠。
- WAL 模式运行时会有 `kirameku.db-wal` / `kirameku.db-shm` 两个伴随文件；它们不是独立备份，备份必须走在线备份 API（见 §10.7）。

```ts
// server/db/schema/post.ts
import { sql } from "drizzle-orm";
import {
  check,
  index,
  integer,
  sqliteTable,
  text,
} from "drizzle-orm/sqlite-core";
import { category } from "./category";

export const post = sqliteTable(
  "post",
  {
    id: integer("id").primaryKey({ autoIncrement: true }),
    title: text("title").notNull(),
    slug: text("slug").notNull().unique(),
    description: text("description").notNull().default(""),
    content: text("content").notNull().default(""),
    cover: text("cover").notNull().default(""),
    categoryId: integer("category_id").references(() => category.id, {
      onDelete: "set null",
    }),
    status: text("status").notNull().default("draft"),
    isPinned: integer("is_pinned", { mode: "boolean" })
      .notNull()
      .default(false),
    views: integer("views").notNull().default(0),
    likes: integer("likes").notNull().default(0),
    wordCount: integer("word_count").notNull().default(0),
    readingTime: integer("reading_time").notNull().default(0),
    publishedAt: integer("published_at", { mode: "timestamp_ms" }),
    createdAt: integer("created_at", { mode: "timestamp_ms" })
      .notNull()
      .$defaultFn(() => new Date()),
    updatedAt: integer("updated_at", { mode: "timestamp_ms" })
      .notNull()
      .$defaultFn(() => new Date()),
  },
  (t) => [
    index("idx_post_status_published_at").on(t.status, t.publishedAt),
    index("idx_post_category_status").on(t.categoryId, t.status),
    check("post_status_check", sql`${t.status} in ('draft','published')`),
    check("post_pinned_check", sql`${t.isPinned} in (0,1)`),
  ]
);
```

> 示例假设 `created_at` / `updated_at` 在生产库无 `NULL`；如果审计发现 `NULL`，先在迁移脚本里 backfill，或去掉对应 `.notNull()` 并在应用层兜底。不要为了让 schema「好看」而让导入失败。

```ts
// server/db/client.ts
import "server-only";
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import { env } from "@/server/env";
import * as schema from "./schema";

const globalForDb = globalThis as unknown as {
  __sqlite?: Database.Database;
};

function openDatabase() {
  const sqlite = new Database(env.DATABASE_PATH);
  sqlite.pragma("journal_mode = WAL");
  sqlite.pragma("synchronous = NORMAL");
  sqlite.pragma("foreign_keys = ON");
  sqlite.pragma("busy_timeout = 5000");
  sqlite.pragma("cache_size = -20000");
  sqlite.pragma("mmap_size = 268435456");
  sqlite.pragma("temp_store = MEMORY");
  return sqlite;
}

const sqlite = globalForDb.__sqlite ?? openDatabase();
if (process.env.NODE_ENV !== "production") globalForDb.__sqlite = sqlite;

export const db = drizzle(sqlite, { schema });
export { sqlite };
```

写事务必须用同步回调，事务里不能 `await`：

```ts
db.transaction(
  (tx) => {
    tx.insert(post).values({ ... }).run();
    tx.update(category).set({ postCount: sql`${category.postCount} + 1` }).run();
  },
  { behavior: "immediate" }
);
```

> **时间字段说明：** 新库统一存 UTC epoch ms。旧库是 `timestamp without time zone`，PostgreSQL 的 `EXTRACT(EPOCH FROM col)` 会把这个值当作“无时区”的秒数，**不会**使用会话的 `TimeZone`；必须显式写 `EXTRACT(EPOCH FROM (col AT TIME ZONE 'Asia/Shanghai')) * 1000`，先按上海墙上时间转成 `timestamptz` 再取 epoch，避免把本地时间当 UTC 造成 8 小时偏移。展示层用 `Intl.DateTimeFormat("zh-CN", { timeZone: "Asia/Shanghai" })` 格式化；不要再混用 `CURRENT_TIMESTAMP`（TEXT、秒级、UTC）。

### 5.5 迁移策略

> **2026-10-22 历史说明：** 本节描述的一次性 PostgreSQL → SQLite 导入已经执行完毕，`scripts/migrate/*`、`postgres` devDependency 和 `migrate:audit` / `migrate:pg2sqlite` 已删除。以下命令与 manifest 说明仅作历史记录，**不要在当前仓库执行**；当前数据库维护只使用 `pnpm db:migrate`、`pnpm db:backup` / `pnpm db:restore`，以 `Kirameku/server/db/README.md` 为准。

#### 5.5.1 Schema 基线

1. 以**生产库实际结构**为准（`information_schema.columns` + `pg_dump --schema-only`），不要只信 `init_db.sql`。

5. 空库跑 `PRAGMA integrity_check`（应为 `ok`）和 `PRAGMA foreign_key_check`（应为空）。

#### 5.5.2 数据导出/导入

脚本：`scripts/migrate/pg-to-sqlite.ts`。`postgres` 只作为 devDependency 出现在迁移脚本里，运行时依赖中不保留 PostgreSQL 驱动。

流程：

1. 进入维护模式，停止所有写入（旧站只读）。
2. 做一次 `pg_dump -Fc` 冷备份。
3. 按依赖顺序导出：
   `user → category → tag → post → post_tag → github_user → comment → message → chatter → chatter_comment → album → photo → project → friend_link → bookmark_category → bookmark_site → site_config → visitor`。
4. 每条记录保留原 `id`；时间列导出为 `EXTRACT(EPOCH FROM (col AT TIME ZONE 'Asia/Shanghai')) * 1000`（整数 ms，`timestamp without time zone` 必须显式解释时区）；布尔列导出为 `CASE WHEN col THEN 1 ELSE 0 END`；JSON 列先 `JSON.parse` 再 `JSON.stringify` 规范化。
5. SQLite 侧先 `PRAGMA foreign_keys = OFF`，单事务批量插入；提交后执行 `PRAGMA foreign_key_check`，确认无输出，再打开外键。
6. 校验 `sqlite_sequence` / `MAX(id)`，确保后续自增不会撞号。
7. 执行 `PRAGMA integrity_check`，并跑应用层冒烟测试。

```bash
# 冷备份：只做备份，不直接作为导入源
pg_dump -Fc --no-owner --no-privileges "$DATABASE_URL" > /backup/kirameku-$(date +%F).dump

# SQLite 建库 + 迁移
DATABASE_PATH=./data/kirameku.db pnpm db:migrate

# 导入（脚本内部完成类型转换、批量插入、校验）
DATABASE_URL=... DATABASE_PATH=./data/kirameku.db pnpm migrate:pg2sqlite
```

> 不要用 `pg_dump --data-only` 的 SQL 文本直接喂给 SQLite：布尔、时间、`JSONB`、转义规则都不同。导入脚本应通过 `postgres.js` 读取原始值，在 TypeScript 里做显式转换。

#### 5.5.5 切换约束

- **不做双写。** PostgreSQL 与 SQLite 只选一个作为写入源；双写会带来顺序、冲突和回滚复杂度。
- **维护窗口 30–60 分钟。** 停写 → 最终导出 → 导入 → 校验 → 启动新应用。
- **切流后先只读运行 30 分钟。** 通过 `SITE_READ_ONLY=1` 禁用写接口，观察错误率和页面；确认后再开放写入。这样在只读窗口内回滚不需要反向同步。
- **PostgreSQL 保留 30 天。** 期间不删库、不删账号，作为冷回滚目标。
- 如果只读窗口后已经产生新写入，回滚需要 `scripts/migrate/sqlite-to-pg.ts` 反向同步；该脚本属于 P6 交付物，必须在 staging 演练过。

### 5.6 查询与计数

- **文章列表**：一次查询 join `category`，再用二次查询批量取标签（`WHERE post_id IN (...)`），避免逐篇 N+1；不要依赖 PostgreSQL 的 `json_agg`，需要聚合时用 SQLite 的 `json_group_array`，但本项目直接用应用层分组更清晰。
- **评论树**：一次取该文章所有已审核评论 + join `github_user`，在内存组装树（现有逻辑已是内存组装，但用户查询是 N+1）。
- **后台评论**：分页取根评论 + 一次取所有子评论 + 一次取用户，避免递归查询。
- **浏览量**：`UPDATE post SET views = COALESCE(views, 0) + 1 WHERE id = ?` 原子自增；由客户端 `POST /api/posts/[id]/view` 触发，按 `sessionStorage + IP/日期` 去重。
- **点赞**：`UPDATE post SET likes = MAX(0, COALESCE(likes, 0) + ?) WHERE id = ?`；SQLite 没有 `GREATEST`，用标量 `MAX(a,b)`。一期不做账号级去重，二期可加 `reaction` 表。
- **冗余计数**：分类/标签/说说评论数在事务内更新；每日 cron 跑一次 `scripts/reconcile-counts.ts` 修正漂移。
- **分页**：一期继续 `OFFSET/LIMIT`（数据量小）；文章/访客超过 10 万后再改 keyset。
- **查询预算**：单条查询 P95 < 20ms；禁止无索引的 `LIKE '%...%'`、全表 `ORDER BY`、在请求路径做全量统计。`better-sqlite3` 是同步的，慢查询会直接卡住事件循环。

```ts
// server/http/handler.ts
import { ZodError } from "zod";
import { AppError } from "./errors";

export async function handle<T>(fn: () => Promise<T>): Promise<Response> {
  try {
    return Response.json(await fn());
  } catch (err) {
    if (err instanceof ZodError) {
      return Response.json(
        { error: { code: "VALIDATION_ERROR", message: "参数校验失败", details: err.flatten() } },
        { status: 422 }
      );
    }
    if (err instanceof AppError) {
      return Response.json(
        { error: { code: err.code, message: err.message } },
        { status: err.status }
      );
    }
    console.error(err);
    return Response.json(
      { error: { code: "INTERNAL_ERROR", message: "服务器内部错误" } },
      { status: 500 }
    );
  }
}
```

## 7. 认证与安全设计

### 7.1 身份模型

| 身份 | 登录方式 | Cookie | 权限 |
|:-----|:---------|:-------|:-----|
| 管理员 | 用户名 + 密码 | `kir_admin` | 后台全部读写 |
| GitHub 访客 | GitHub OAuth | `kir_user` | 发表评论/留言/说说评论、点赞、查看自己的信息 |
| 匿名访客 | 无 | 无 | 浏览、点赞（限流）、访客记录 |

两个 Cookie 分开，互不覆盖；管理员也可以额外登录 GitHub 来发评论。

### 7.2 JWT / Cookie 设计

| 项 | 设计 |
|:---|:-----|
| 算法 | HS256（`jose`） |
| 密钥 | `AUTH_SECRET`，≥32 字节随机值 |
| Admin claims | `{ sub: user.id, aud: "admin", role: "admin", ver: 1 }` |
| User claims | `{ sub: githubUser.id, aud: "github", login, ver: 1 }` |
| Admin TTL | 72 小时（沿用现有） |
| User TTL | 30 天 |
| Cookie flags | `httpOnly`, `secure`（生产）, `sameSite: "lax"`, `path: "/"` |
| 刷新 | 一期不做 refresh token；过期重新登录；后续可加滑动续期 |
| 注销 | `POST /api/auth/logout` 清 Cookie |

> **关键修复**：校验时必须同时检查 `aud` 和 `role`。GitHub 用户 token 的 `aud` 是 `github`，永远不能通过 `requireAdmin()`。这直接关闭了 §1.5 第 11 条漏洞。

```ts
// server/auth/guard.ts
import "server-only";
import { cookies } from "next/headers";
import { jwtVerify } from "jose";
import { db } from "@/server/db/client";
import { users } from "@/server/db/schema";
import { eq } from "drizzle-orm";
import { AppError } from "@/server/http/errors";

const secret = new TextEncoder().encode(process.env.AUTH_SECRET);

export async function getAdminSession() {
  const token = (await cookies()).get("kir_admin")?.value;
  if (!token) return null;
  try {
    const { payload } = await jwtVerify(token, secret, { audience: "admin" });
    if (payload.role !== "admin") return null;
    const [user] = await db.select().from(users).where(eq(users.id, Number(payload.sub))).limit(1);
    return user?.isAdmin ? user : null;
  } catch {
    return null;
  }
}

export async function requireAdmin() {
  const admin = await getAdminSession();
  if (!admin) throw new AppError("UNAUTHORIZED", "请先登录", 401);
  return admin;
}
```

### 7.3 GitHub OAuth 流程

```
1. GET /api/auth/github/login
   - 生成随机 state，写入短时 Cookie `kir_gh_state`（httpOnly, 10 分钟）
   - 302 到 GitHub authorize（scope=read:user）
2. GET /api/auth/github/callback?code=...&state=...
   - 校验 state
   - code 换 access_token（服务端 POST）
   - 拉 GitHub /user
   - upsert github_user
   - 签发 `kir_gh` Cookie（httpOnly, 30 天, SameSite=Lax）
   - 清除 state Cookie
   - 302 到 `${FRONTEND_ORIGIN}/auth/callback`（URL 不带 token）
3. 前端不再读 URL token，不写 localStorage 凭据
   - 仅缓存 `github_user` 公开资料用于首屏，挂载后用 `/api/auth/github/me` 校验
```

### 7.5 CSRF / CORS / 限流

- **CORS**：删除 `CORSMiddleware` 和 `CORS_ORIGINS`；同源部署。
- **CSRF**：
  - Cookie `SameSite=Lax`。
  - Server Actions 由 Next 校验 Origin。
  - Route Handler 的写操作校验 `Origin`/`Sec-Fetch-Site`，非同源返回 403。
  - 后台敏感操作（删除、清空、改密）可加二次确认 + 短时 `X-CSRF-Token`（双提交）。
- **限流**（单进程内存令牌桶，按 IP + 路由）：
  | 路由 | 限制 |
  |:-----|:-----|
  | `POST /api/auth/login` | 5 次/分钟/IP，失败计数 |
  | `POST /api/comments` | 5 次/10 分钟/IP |
  | `POST /api/messages` | 5 次/10 分钟/IP |
  | 点赞/取消 | 30 次/分钟/IP |
  | `POST /api/visitors/record` | 10 次/分钟/IP |
  | `POST /api/admin/upload/image` | 20 次/小时/管理员 |
  | `/api/uapis` | 60 次/分钟/IP |
  | `/api/music` | 30 次/分钟/IP |
- 限流是进程内内存态；本项目明确禁止多实例，因此单实例足够。未来若拆分，需要换 Redis 等共享存储。

### 7.6 上传安全

```ts
// server/storage/image.ts
import sharp from "sharp";

const ALLOWED = new Set(["image/jpeg", "image/png", "image/webp", "image/gif"]);
const MAX = 10 * 1024 * 1024;

export async function validateAndDescribe(file: File) {
  if (!ALLOWED.has(file.type)) throw new AppError("UNSUPPORTED_MEDIA_TYPE", "仅支持 JPG/PNG/WebP/GIF", 415);
  if (file.size > MAX) throw new AppError("PAYLOAD_TOO_LARGE", "文件不能超过 10MB", 413);

  const buf = Buffer.from(await file.arrayBuffer());
  const meta = await sharp(buf).metadata(); // 失败即不是有效图片
  const width = meta.width ?? 0;
  const height = meta.height ?? 0;
  return {
    buf,
    width,
    height,
    orientation: width >= height ? "landscape" : "portrait",
    ext: meta.format === "jpeg" ? "jpg" : meta.format ?? "webp",
  };
}
```

- **禁止 SVG**（或单独走 sanitize + `Content-Disposition: attachment`）。
- 文件名用 `crypto.randomUUID()`，不信任原始扩展名。
- OSS 对象设置 `Content-Type` 为真实格式；如使用自定义域名，确保不会把用户上传的 HTML 当页面执行。
- 上传接口仅管理员可用；返回 URL + 宽高 + 方向。

### 7.7 XSS / SSRF / HTML 清洗

- 文章 Markdown：`marked` 渲染后使用 `rehype-sanitize`/`DOMPurify` 清洗（服务端用 `sanitize-html` 或 `rehype` 管线）。
- 评论/留言：始终按纯文本渲染，不解析 Markdown。
- 外部 URL（友链/项目链接）只做展示，服务端不主动抓取；如需抓 favicon，走白名单/超时。

### 7.8 隐私与访客数据

- 访客 IP 默认保留 90 天，之后由 cron 删除或匿名化（保留城市/运营商，IP 置空/哈希）。
- 提供 `VISITOR_RETENTION_DAYS` 环境变量。
- 不做跨站追踪；`VisitorTracker` 只用 `sessionStorage` 记录一次。
- 站点隐私说明中写明收集字段（IP、UA、路径、地理位置）。
- 地理查询失败时静默降级，不阻塞页面。

## 8. 功能模块设计

### 8.1 公共站点

#### 首页 `/`

- **服务端**：`getHomeData()` 并行取：
  - 已发布文章数、说说数、照片数
  - 最新 4 篇文章
  - 最新 5 条说说
  - 相册预览（前 6 张）
- **客户端**：`HomeClient` 只保留轮播/动画/交互；初始数据由 props 注入，不再 `useEffect` 拉首屏。
- **缓存**：60 秒；文章/说说/相册写操作后 `revalidateTag("home")`。
- **注意**：Live2D、3D 背景等重组件用 `dynamic(..., { ssr: false })` 懒加载，避免拖慢 LCP。

#### 文章列表 `/posts`

- 用 `searchParams` 表达状态：`?category=tech&page=2`。
- 服务端取分类和第一页文章；客户端 `PostsExplorer` 负责切换分类/加载更多（调用 `/api/posts`）。
- 分类计数只统计已发布文章（修复现有包含草稿的问题）。
- 保留现有卡片、动画、空状态。

#### 文章详情 `/posts/[slug]`

- 服务端取文章 + 已审核评论树；`generateMetadata` 输出 SEO/OG。
- **浏览量**：详情查询不自增；客户端挂载后 `POST /api/posts/{id}/view`，服务端按 `sessionStorage` 标记 + IP/日期去重。

### 8.4 仪表盘统计

用 SQL 聚合，避免把全表读进内存：

```sql
-- 30 天文章趋势（published_at 是 epoch ms；按 Asia/Shanghai 分日）
SELECT date(published_at / 1000, 'unixepoch', '+8 hours') AS date,
       count(*) AS count
FROM post
WHERE status = 'published'
  AND published_at >= (unixepoch('now') - 30 * 86400) * 1000
GROUP BY 1
ORDER BY 1;

-- 浏览器分布
SELECT coalesce(nullif(browser, ''), '未知') AS name, count(*) AS value
FROM visitor
GROUP BY 1
ORDER BY 2 DESC;
```

- 补全 30 天空日期在应用层做。
- 分类分布只统计 `post_count > 0`。
- 统计接口需要 admin；不再公开。

## 10. 部署与运维

### 10.1 目标拓扑

```
Internet
  │
  ▼
Caddy (443, TLS)              ← 独立的 compose 项目（或自带 caddy 容器 / 宿主机进程）
  │  reverse_proxy kirameku-app:3000（共享网络 kirameku-edge）
  ▼
Next.js 容器（pnpm start）     ← 从 GHCR 拉取的镜像
  │
  ├── SQLite 文件 /data/db/kirameku.db（WAL，宿主机 ./data bind mount）
  ├── 阿里云 OSS
  └── 外部 API（GitHub/天气/音乐）
```

- 不再需要 8000/8085/5173 端口，也不需要 PostgreSQL 进程。
- 反代不再按 `/api`、`/uploads`、`/reader3` 分流；未命中的路径直接 404。
- 只有一个 Node 进程；PM2/systemd/Docker 任选其一。
- **只能有一个实例写同一个 SQLite 文件**；发布必须先停旧实例（stop-the-world），不能双实例并行。
  `docker compose up -d` 本身是先停后起，符合该约束。
- **镜像在 CI 构建，服务器不编译。** 生产机只执行 `docker compose pull` + `up -d`。

> **2026-10-22 落地说明：** 入口反代由 Nginx 改为 Caddy。Caddy 跑在独立的 compose 项目里，
> 通过外部网络 `kirameku-edge` 反代 `kirameku-app:3000`（见 §10.3）；本项目不发布宿主机端口。
> 自带 Caddy（`docker-compose.caddy.yml`）与宿主机反代（`docker-compose.host-proxy.yml`）为备选形态。

### 10.2 Dockerfile（建议）

> **2026-10-22 落地说明：** 实际部署文件为仓库根目录 `docker-compose.yml` + `Kirameku/Dockerfile`，采用多阶段 `pnpm start` 方案（不启用 `output: "standalone"`），以便容器内继续运行 `tsx` 维护脚本。下方为最初建议，保留作设计参考。

```dockerfile
# syntax=docker/dockerfile:1

ENV PNPM_HOME=/pnpm

RUN corepack enable

FROM base AS deps

FROM base AS runner

    && mkdir -p /data && chown nextjs:nodejs /data

COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

```

`next.config.mjs` 增加（当前实现使用原生 ESM，避免 Node 26 下 `tsx` 加载配置的告警）：

```ts
  compress: true,

    remotePatterns: [
```

### 10.3 反向代理：与既有 Caddy 共享网络（默认）

> **2026-10-22 修正：** 生产上的 Caddy 早已存在于**另一个 compose 项目**中，不是本项目自带的，
> 也不是宿主机进程。容器里的 Caddy 无法访问宿主机的 `127.0.0.1`，因此原先「只 `expose`、由自带
> caddy 反代 `app:3000`」的形态在上线时会直接 502。现改为：本项目不发布任何宿主机端口，把 `app`
> 接入外部网络 `kirameku-edge` 并固定别名 `kirameku-app`，由既有 Caddy 反代这个名称；自带 Caddy
> 退化为 opt-in 的 `docker-compose.caddy.yml`。

```yaml
# docker-compose.yml（节选）
services:
  app:
    expose: ["3000"]
    networks:
      edge:
        aliases: [kirameku-app]     # 稳定的跨项目 DNS 名
networks:
  edge:
    external: true
    name: ${SHARED_NETWORK:-kirameku-edge}
```

既有 Caddy 项目侧：

```yaml
services:
  caddy:
    networks: [default, kirameku]
networks:
  kirameku:
    external: true
    name: kirameku-edge
```

```caddyfile
boke.hiromu.top {
	encode zstd gzip
	request_body {
		max_size 12MB
	}
	reverse_proxy kirameku-app:3000
}
```

要点：

- 网络由 `scripts/deploy-server.sh` 保证存在（`docker network inspect` 失败则 `docker network create`），
  且它不归属任何 compose 项目，所以 `docker compose down` 不会把它连根删掉、把反代后端抽走。
- 别名必须是 `kirameku-app` 而不是 compose 服务名 `app`：`app` 过于通用，同一网络上若有别的
  项目也叫 `app` 就会串。
- 反代侧**不能**写 `127.0.0.1:3000`——在 Caddy 容器里那指向 Caddy 自己。
- `reverse_proxy` 自动写入 `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host`，
  `Kirameku/server/http/ip.ts` 与 `Kirameku/server/http/origin.ts` 依赖这些头。
- Caddy 不改写任何缓存头：Next.js 自己已对 `/_next/static/*` 发 `immutable`、对 HTML 发 `s-maxage=60`。
  在反代再设一次会让每个静态资源出现两条 `Cache-Control`（实测确认）。
- `request_body max_size 12MB` 是硬限制，超过时 Caddy 直接返回 413，请求不会进到应用。
  注意它只在实际读取请求体时触发：不读 body 的路由收到超大请求仍会返回 200。
- 证书与 ACME 账号属于既有的 Caddy 项目，本项目完全不碰。

另有两种非默认形态：

| 场景 | 做法 |
|:--|:--|
| 服务器上没有别的反代 | `docker compose -f docker-compose.yml -f docker-compose.caddy.yml up -d`，由本项目起 `caddy:2-alpine`，挂载根目录 `Caddyfile`，证书存 `caddy-data` 卷 |
| 反代是宿主机进程（systemd Caddy / Nginx） | `docker compose -f docker-compose.yml -f docker-compose.host-proxy.yml up -d app`，把 `app` 绑回 `127.0.0.1:3000`；`DEPLOY_COMPOSE_FILE` 设成两个文件、`DEPLOY_SERVICES=app` |

> 自带 Caddy 时 `Caddyfile` 是**单文件** bind mount，改了它要
> `docker compose up -d --force-recreate caddy`（`up -d` 不会因为文件内容变化而重建 caddy；
> 编辑器换 inode 后容器内文件会消失，`caddy reload` 报 `no such file or directory`）。

```nginx

    server_name boke.hiromu.top;
```

### 10.5 构建与发布

**CI（GitHub Actions 示例）**

```yaml
name: ci
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    env:
      DATABASE_PATH: ./.tmp/ci.db
      AUTH_SECRET: test-secret
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: mkdir -p .tmp
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm db:migrate
      - run: pnpm test
      - run: pnpm build
```

- 不再需要 PostgreSQL service / Testcontainers；每个测试 worker 用独立临时 SQLite 文件。
- `pnpm build` 使用 `.tmp/ci.db`，**绝不能指向生产数据文件**；构建期页面应动态渲染，不依赖预渲染查库。
- 迁移脚本的完整演练需要 PostgreSQL，随旧栈一并退役（见附录 C C.1），日常 CI 只跑空库迁移。

**发布（当前实现：CI 构建镜像 + 服务器拉取）**

实际落地的流水线是 `.github/workflows/release.yml`：

1. `verify` —— 复用 `.github/workflows/verify.yml`，跑 typecheck → 单测 → 空库迁移 → 生产构建。
   任一步失败都不会产出镜像，因此发布链路自带质量门。PR 由 `.github/workflows/ci.yml` 复用同一个文件。
2. `image` —— `docker/build-push-action` 构建 `linux/amd64` + `linux/arm64`，推送到
   `ghcr.io/<owner>/kirameku-lite`（由 `${GITHUB_REPOSITORY,,}` 派生，避免与同名旧包冲突），
   标签为 `latest`（仅默认分支）、`v*`、`sha-<短 commit>`；
   缓存用 `type=gha`。
3. `deploy` —— 仅在 `main` 分支执行，通过 SSH 把 `scripts/deploy-server.sh` 流式送到服务器运行
   （GHCR token 走 stdin，不落进程列表也不落服务器 `~/.docker`）。

`scripts/deploy-server.sh` 的顺序：

1. 校验 `.env` 与 compose 文件存在。
2. 记录当前容器镜像 ID（回滚用）。
3. `docker compose exec app pnpm db:backup --prune` 备份 SQLite + uploads 归档（`BACKUP_BEFORE_DEPLOY=0` 可跳过）。
   注意：这条命令必须带 `</dev/null`，否则它会吞掉经 SSH `bash -s` 从 stdin 流式传入的脚本剩余部分，
   部署会静默地只做完备份就以 0 退出。
4. `docker compose pull` → `docker compose up -d`；容器 entrypoint 先执行 `pnpm db:migrate`，
   天然满足「先停旧实例再迁移」的单写者约束（`up -d` 是先停后起）。
5. 轮询 `docker inspect` 的 healthcheck 状态（默认 180 秒）。
6. 健康则清理悬空镜像；不健康则打印日志、用上一个镜像 ID `up -d` 回滚并复检。
7. 健康通过后安装/刷新 systemd timer `kirameku-maintenance.timer`，每天跑 `scripts/maintenance.sh`
   （见 §10.7、§10.9）；没有免密 sudo 时打 WARNING 并继续，不阻塞发布。

相关仓库配置：Secrets `DEPLOY_HOST` / `DEPLOY_USER` / `DEPLOY_SSH_KEY` / `DEPLOY_PORT` /
`DEPLOY_KNOWN_HOSTS`，Variables `DEPLOY_PATH`（默认 `/srv/kirameku`）、`DEPLOY_COMPOSE_FILE`、
`DEPLOY_SERVICES`、`DEPLOY_ENABLED`。手工回滚：
`IMAGE_REF=ghcr.io/<owner>/kirameku-lite:sha-<commit> bash scripts/deploy-server.sh`。

> 初稿设想的「服务器解压 standalone tarball + 切软链 + systemd 重启」不再使用：镜像本身即不可变产物，
> 回滚粒度是镜像 ID，比软链切换更直接。

### 10.6 资源与性能

- 服务器 1.8GB：Next standalone 正常 RSS 约 250–500MB；SQLite page cache 约 20MB；不再有 PostgreSQL 进程，内存比旧架构更宽裕。图片上传并发限 2–3。
- 构建在 CI/本地完成；服务器只运行产物。
- `NODE_OPTIONS=--max-old-space-size=768` 可作为兜底。
- 监控：`/api/health` 检查 DB（`SELECT 1`、文件可写、迁移版本）；`/api/internal/metrics`（`CRON_SECRET`）记录 event loop lag、内存、请求 P95、`SQLITE_BUSY` 次数、DB/WAL 文件大小，以及备份新鲜度（`backups.latest_age_s`、`uploads_archives`）和磁盘余量（`disk.available_bytes`）。
- 慢查询：开发环境打开 Drizzle 日志；生产只记录 >100ms 的查询（`better-sqlite3` 同步执行，慢查询会阻塞所有请求）。
- 静态资源交给 Caddy/Next 缓存；OSS 图片走 CDN/自定义域名。
- 磁盘：DB 增长主要来自访客/评论；按保留期清理并每周 `incremental_vacuum`，把磁盘使用率纳入告警。磁盘写满时 SQLite 会直接写失败。

### 10.7 备份与恢复

- **每日在线备份**：`pnpm db:backup` 用 `better-sqlite3` 的 `db.backup()` 生成一致性副本（内部使用 SQLite Online Backup API），对副本执行 `PRAGMA integrity_check`。保留 14 天每日 + 8 周每周（按 ISO 周），成组删除。
- **备份是「组」不是单文件**：`kirameku-<ts>.db` + `kirameku-<ts>.db.meta.json` + `kirameku-<ts>-uploads.tar.gz`。uploads 归档解决「配了本地存储时图片不在数据库里、只备份 db 等于恢复出一堆坏链接」的问题；配了 OSS 时用 `--no-uploads` 跳过。归档失败只写 `meta.uploadsError`，不让脚本以非 0 退出（部署脚本会把非 0 当成「完全没有备份」）。
- **不要直接 `cp kirameku.db`**：WAL 模式下未 checkpoint 的数据在 `-wal` 文件里，直接复制可能得到不一致或缺少最新事务的副本。
- `meta.json` 记录行数、迁移版本、文件大小、SHA-256 以及 uploads 归档的 sha256 与条目数，恢复时可校验。
- **恢复步骤**：停应用 → 跑 `pnpm db:restore <backup.db> --target /data/db/kirameku.db`（`--with-uploads` 同时校验并解包图片）→ 校正属主 → 启动 → 冒烟测试。
- **定时化**：备份不再只发生在发版时。`scripts/deploy-server.sh` 装一个 systemd timer，每天 04:30（`Persistent=true`，跨停机补跑）执行 `scripts/maintenance.sh`：`db:backup --prune` → `db:prune-visitors` → `db:reconcile-counts`。日志写 `logs/maintenance.log`，按大小滚动；手动执行用同一个 `flock`，不会与 timer 并发。
- **新鲜度可观测**：`/api/internal/metrics` 的 `backups.latest_age_s` 超过 26 小时即说明 timer 没跑成，不需要登服务器翻目录。
- 每月做一次恢复演练（到临时目录，跑迁移 + 关键查询），不要只验证「备份文件存在」。
- 迁移前额外做一次手动快照：PostgreSQL `pg_dump -Fc` + SQLite 空库/当前库各一份。
- 可选：Litestream 持续复制到 S3/OSS。它是独立 sidecar 进程，不是应用进程；一期不作为默认方案，若启用需单独监控复制延迟。
- OSS 开启版本控制/合规保留（按成本决定）。

### 10.8 日志与监控

- `pino` JSON 日志：`level, time, requestId, method, path, status, durationMs, actorId, errorCode`。
- 错误日志包含 stack（仅服务端）；响应不返回 stack。
- 反代（Caddy）access/error log 保留 14 天；容器日志用 `docker compose logs --since` 检索。
- **容器日志必须有上限**：默认 json-file 驱动会把日志一直写到磁盘满。`docker-compose.yml` 设为 `max-size: ${KIRAMEKU_LOG_MAX_SIZE:-100m}` + `max-file: ${KIRAMEKU_LOG_MAX_FILE:-3}`，改完 `up -d` 重建容器生效。
- 可选 Sentry（前后端）；采样率 0.1–0.2。
- 关键告警：5xx 比例、登录失败激增、OSS 上传失败、`SQLITE_BUSY` 激增、WAL 文件异常增长、磁盘不足。

### 10.9 定时任务

单进程不需要额外 worker。实际落地的是一个 systemd timer，而不是让每条任务各自去路由：

| 任务 | 频率 | 入口 |
|:-----|:-----|:----------|
| 备份（db + uploads + 保留策略） | 每日 | `pnpm db:backup --prune`（由 `scripts/maintenance.sh` 调用） |
| 访客 IP 清理 | 每日 | `pnpm db:prune-visitors` |
| 计数校准 | 每日 | `pnpm db:reconcile-counts` |
| 健康检查 | 外部探活 | `GET /api/health` |
| 运维快照 | 按需 | `GET /api/internal/metrics`（`CRON_SECRET`） |

- `scripts/maintenance.sh` 是唯一入口：`flock -n` 保证单实例，任一步失败以非 0 退出并记进 `logs/maintenance.log`；所有 `docker compose exec` 都带 `</dev/null`，否则在 cron/systemd 下会挂住。
- timer 由 `scripts/deploy-server.sh` 在每次健康发布后写入 `/etc/systemd/system/kirameku-maintenance.{service,timer}`，因此上线时不需要手工加 cron；没有免密 sudo 时脚本跳过并提示改用手工 cron。
- 如果未来确实需要 HTTP 触发（例如从外部调度器调用），保持 `CRON_SECRET` 鉴权 + 幂等；单实例下不需要分布式锁，拆分前必须先把锁迁移到共享存储。

### 12.4 回滚方案

**触发条件**：P0 故障（无法登录/无法发文/大面积 500/数据异常）且 30 分钟内无法修复。

**情况 A：只读观察窗口内（推荐路径）**

1. Nginx upstream 切回旧前台 3000 + `/api` 8000（不再有 `/reader3`）。
2. 启动旧栈；PostgreSQL 仍是 T0 的完整数据，**无需恢复数据库**。
3. 停止新应用，保留 SQLite 文件供排查。
4. 目标恢复时间：30 分钟内。

**情况 B：已开放写入之后**

1. 立即停止新应用写入（`SITE_READ_ONLY=1` 或停进程）。
2. 运行 `scripts/migrate/sqlite-to-pg.ts`，把 T0 之后的增量写回 PostgreSQL；脚本必须幂等并按 `id` upsert。
3. 校验 PostgreSQL 行数/内容；确认无冲突。
4. 切回旧栈。
5. 如果反向同步不可用或校验失败：明确记录 T0 之后的新写入，评估是否接受丢失；**不要**让旧 FastAPI 直接读 SQLite（它不支持）。

**前提：**

- 旧环境变量、旧构建产物、旧 Nginx 配置保留至少 30 天。
- 回滚只恢复博客功能，**不恢复小说**；旧前台若仍含小说入口，Nginx 对 `/novel`、`/reader3` 返回 404，`reader-master` 保持停止。
- PostgreSQL 在 30 天内保持可恢复，不要提前删库。
- 回滚演练 A 必须在 staging 至少做一次；B 若实现也要演练。
- 保留 SQLite 文件和 `migration-manifest.json`，便于复盘。

## 13. 风险与对策

| 风险 | 概率 | 影响 | 对策 | 触发降级 |
|:-----|:----:|:----:|:-----|:---------|
| PostgreSQL→SQLite 数据迁移失败/类型丢失 | 中 | 高 | 脱敏副本 dry-run；行数/ID/哈希/NULL 校验；保留 PG 30 天；反向同步脚本 | 修复脚本重跑；必要时切回旧栈 |
| SQLite 单写者导致 `SQLITE_BUSY`/写延迟 | 中 | 中 | WAL、`busy_timeout`、短事务、`BEGIN IMMEDIATE`、重试、单实例 | 写队列；极端情况评估 libSQL/PG（超出本期） |
| SQLite 文件损坏/磁盘故障 | 低 | 高 | 本地 SSD、每日在线备份、`integrity_check`、UPS、恢复演练 | 从备份恢复；保留 WAL 供排查 |
| 误部署多实例/把 DB 放 NFS | 中 | 高 | 部署检查清单；单副本；禁止 NFS；启动时检测第二个进程 | 立即停一个实例；迁回本地盘 |
| `better-sqlite3` 同步阻塞事件循环 | 中 | 中 | 查询预算 <20ms；索引；批量事务；event loop lag 告警 | 用 worker thread 或异步驱动重构热点 |
| 后台功能遗漏 | 中 | 中 | 功能矩阵逐项验收；先 CRUD 后体验 | 缺失项排到 P5，不阻塞切流 |
| SEO 排名下降 | 中 | 中 | 保持 URL；metadata/sitemap/301；上线前爬虫对比 | 修复 canonical/重定向 |
| 1.8GB 内存不足 | 中 | 中 | standalone；构建在 CI；SQLite 缓存 20MB；并发限制；监控 | 升级内存/拆分构建 |
| 认证迁移导致老用户重新登录 | 高 | 低 | 明确公告；Cookie 新会话；不兼容旧 localStorage token | 可短期兼容 Bearer（不推荐） |
| 外部 API 不稳定（音乐/天气） | 中 | 中 | 缓存、超时、兜底 UI、降级 | 隐藏对应工具/模块 |
| 动画/视觉回归 | 中 | 低 | Playwright 截图；保留组件；人工验收 | 回退具体组件 |
| 范围蔓延 | 高 | 中 | 非目标清单；阶段门禁；新需求进 backlog | 拒绝插入当前阶段 |
