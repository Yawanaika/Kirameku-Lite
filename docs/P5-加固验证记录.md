# P5 加固与单进程收口记录

日期：2026-10-22

## 本轮范围

P0–P3.2 已完成后的联调与加固。目标是把「运行时依赖旧后端」的最后几处残留清掉，并关闭方案 §7.9 中仍开放的 P0/P1/P2 项。P5.1–P5.3 没有删除 `Kirameku-backend/`；2026-10-22 用户确认下线条件满足后，P5.4 已完成删除。

## 变更清单

### 1. 单进程收口

- 删除 `Kirameku/next.config.mjs` 中最后两条 FastAPI fallback rewrite：
  - `/api/:path*` → `http://127.0.0.1:8000/api/:path*`
  - `/uploads/:path*` → `http://127.0.0.1:8000/uploads/:path*`
- 未命中的 `/api/*`、`/uploads/*` 现在直接返回 404，不再可能被代理到旧服务。
- 补齐 `app/uploads/[...path]/route.ts`。P3.1 记录里写了这个路由，但仓库中实际不存在，导致本地兜底上传写入成功却无法读取（本轮 smoke 首次抓出）。实现复用 `server/storage/local.ts` 的 `readLocalImage()`：路径穿越防护、仅图片扩展名、`nosniff`、`Content-Disposition: inline`、一年 immutable 缓存。
- 生产仍建议由 Nginx `alias` 直接服务 `UPLOAD_DIR`，Node 路由作为 standalone 兜底。

### 2. 服务端 Markdown 与清洗

- 新增 `lib/markdown.ts`：`remark-parse → remark-rehype → rehype-sanitize → rehype-highlight → rehype-stringify`。
  - 先清洗、后高亮，既去掉作者写入的 `<script>`、事件属性、`javascript:` URL，又保留高亮器生成的 `hljs-*` 类。
  - 文件带 `server-only`，客户端无法误引用。
- `/about` 与 `/posts/[slug]` 都改用该管线；`highlight.js` 主题移到根布局统一加载。
- 文章详情不再在客户端 `marked.parse(post.content)`：RSC 产出 `contentHtml` 交给客户端，移除 `marked` 与 14 个 `highlight.js` 语言包的客户端引入。
- 通过 `Omit<PostDetail, "content">` 不再把原始 Markdown 放进 RSC 载荷，页面源码中已无 `content` 字段（smoke 验证 `raw_content_in_rsc=0`）。
- 新增依赖 `rehype-sanitize`；同步移除未使用的 `ali-oss` / `@types/ali-oss`。保留 `sharp`：它是 Next 生产图片优化的可选运行时依赖，且已列入 `pnpm-workspace.yaml` 的 `allowBuilds`。

### 3. 浏览量上报

- `postsService.incrementView(id)`：只对 `status = 'published'` 的文章原子自增，返回最新值；草稿与不存在的 ID 返回 404。
- 新增 `POST /api/posts/[slug]/view`（URL 段沿用历史 `[slug]` 命名，实际传数字 ID，与 `/like` 一致）：
  - `assertWritable` + `assertSameOrigin`；
  - `tryConsumeRateLimit("post-view:{ip}:{id}:{day}", 1, 24h)` 做服务端幂等：同一 IP、同一文章、同一天只计一次；
  - 未计数时返回 `{ counted: false }`，不报 429。
- 客户端在 hydration 后用 `localStorage` 记录 `slug → 日期`，每天最多请求一次；请求失败不影响阅读。
- 验证：连续三次上报返回 `counted:true, views:2` → `counted:false` → `counted:false`，详情页计数与数据库一致。

### 4. 公开写接口限流

方案 §7.5 的限流表已全部落地（此前只有登录/访客/上传/外部代理）：

| 路由 | 限制 | 键 |
|:-----|:-----|:---|
| `POST /api/comments` | 5 次 / 10 分钟 | IP |
| `POST /api/messages` | 5 次 / 10 分钟 | IP |
| `POST /api/chatters/comments` | 5 次 / 10 分钟 | IP |
| 文章/评论/说说/说说评论/留言的点赞与取消 | 30 次 / 分钟 | IP，like/unlike 共享预算 |
| `POST /api/auth/login` | 5 次 / 分钟（仅失败计数） | IP |
| `POST /api/visitors/record` | 10 次 / 分钟 | IP |

| `GET /api/uapis` | 60 次 / 分钟 | IP |
| `GET /api/music` | 30 次 / 分钟 | IP |

新增 `enforceIpRateLimit(request, route, limit, windowMs)` 统一按 `x-forwarded-for` / `x-real-ip` 取 IP，避免 13 个路由重复拼 key。验证：未登录连续提交评论，前 5 次 `401`，第 6 次 `429`。

### 5. 外部代理加固

- `/api/uapis`：
  - 路径白名单（票房、热榜、世界时间、手机归属地、快递、程序员历史、GitHub 用户/仓库）；
  - 拒绝 `..`、非常规字符和未列出的路径（400/403）；
  - GET 结果 5 分钟进程内缓存（`TtlCache`，上限 200 条），带 `max-age=300`；
  - 上游 10 秒超时，连接失败/超时统一 502；POST 仅允许 `search/aggregate`，不缓存。
- `/api/music`：
  - `id` / `ids` 必须是数字，`ids` 最多 50 个；
  - 10 分钟缓存（按歌单/歌曲集合），`max-age=600`；
  - 单曲获取失败不影响整张歌单；上游异常统一 502。
- 新增 `server/http/ttl-cache.ts`（含过期、容量淘汰、clear 测试）。

### 9. GitHub 登录态迁移到 httpOnly Cookie

关闭方案 §7.9 最后一项 P0「token 暴露面过大」。此前 GitHub 登录仍沿用旧实现：回调 URL 带 `?token=`，前端写入 `localStorage.github_token`，写接口用 `Authorization: Bearer` 传递。

- 新增 `kir_gh` HttpOnly Cookie（30 天，`Path=/`、`SameSite=Lax`、生产 `Secure`），与管理员 `kir_admin` 使用不同的 JWT audience。
- `GET /api/auth/github/callback` 校验收到的 `state` 后，直接 `Set-Cookie: kir_gh=<JWT>` 并清除 `kir_gh_state`；302 到 `/auth/callback`，URL 不再携带 token。
- `userFromRequest()` 只从 `kir_gh` Cookie 取会话；`Authorization: Bearer` 不再被接受。
- 新增 `POST /api/auth/github/logout`：同源检查后返回 `Set-Cookie` 清除 `kir_gh`。
- 前端移除 `github_token`、`getToken()` 和所有 `Authorization` 头；`/api/auth/github/me` 只用于校验 Cookie 并返回公开资料。`localStorage` 仅缓存 `github_user`（login/avatar/bio），作为首屏占位，挂载后仍以 `/me` 结果为准；旧 `github_token` 会在挂载时删除。
- 回调页不再读取 `useSearchParams`，`/messages` 的 Suspense 边界随之移除；`github_redirect` 只接受以单个 `/` 开头的站内路径，避免开放重定向。

测试覆盖：服务层 Cookie 读取与 Bearer 拒绝、回调路由写入会话 Cookie 且 Location 不含 token、state 不匹配/授权取消 400、`readCookie` 边界、Cookie 属性。总计 27 个测试文件 / 142 个测试。

## 与方案不一致之处（有意为之）

1. **未实现「首次登录强制改密」。** 方案 P0 的原始问题是旧库自带 `admin123` 默认账号。当前实现里根本不存在默认账号：`pnpm db:seed-admin` 必须显式提供 `ADMIN_PASSWORD`（≥12 位、≤72 字节），否则直接失败；后台已提供改密入口。强制首登改密需要新增 `must_change_password` 列、迁移、会话声明和重定向逻辑，收益低于维护成本，暂不做。
2. **文本内容仍按纯文本渲染。** 评论、留言、说说不做 Markdown 解析，符合方案 §7.7；`/garden/markdown` 是用户在自己浏览器里输入的本地预览，不落库、不跨用户，未接入服务端清洗。
3. **`sharp` 保留。** 图片校验不依赖它（`server/storage/image.ts` 用容器头解析），但 Next 生产图片优化会用到；它不是业务依赖。
